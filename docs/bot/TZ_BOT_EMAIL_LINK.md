# ТЗ для бота: привязка почты, общая подписка и общий ключ с сайтом

Версия 1 · 13.09.2026 · сайт Atlas Secure (https://qodev.dev) ↔ Telegram-бот
(Python, `app/services/remnawave_api.py`, `remnawave_premium.py`,
`remnawave_bypass.py`, `purchase_flow.py`).

Документ самодостаточен: всё, что бот должен знать о сайте, — здесь. Модель
сущностей панели, которую бот ведёт сейчас, — `docs/bot/PANEL_USER_MODEL.md`.
Общий контракт остальных вызовов (баланс, рефералы) — `SYNC_TZ.md`.

---

## 1. Цель и принципы

Цель владельца: **«Один человек — одна подписка — один ключ, в боте и на
сайте; всё единое целое, без лишних проблем с ключами.»**

1. **Один ключ.** У связанного человека премиум-подписка — ОДНА сущность
   панели Remnawave. Её `subscriptionUrl` показывают и бот, и сайт. Бот
   больше не заводит для связанного человека отдельный `tg_{id}_premium`.
2. **Сайт — единая точка связки и продления связанной подписки.** Связку
   (бот ↔ аккаунт сайта) выполняет только сайт. Оплату в боте для
   связанного человека бот проводит через `POST /api/bot/extend` — сайт
   сам продлевает общий ключ в панели. Бот не делает `PATCH expireAt`
   общей сущности.
3. **Бот не пишет почту в панель сам.** Почта привязывается только через
   код из письма, которое отправляет сайт. Без правильного кода почта
   никуда не записывается — ни в панель, ни в БД сайта.
4. **Слияние.** Если при связке подписка есть и в боте, и на сайте —
   остаётся сущность с БОЛЬШИМ сроком, её ключ становится общим, вторая
   отключается (`status: DISABLED`, срок не трогаем). Дни НЕ складываются.
5. **Бонус за связку** +7 дней — один раз на аккаунт сайта и один раз на
   Telegram ID, какой бы дорогой ни шла связка. Начисляет сайт.
6. **Обход (bypass) — продукт бота.** Бот продолжает вести `{telegram_id}`
   как раньше. Сайт знает о нём, показывает остаток и в следующей фазе
   сможет докупать трафик в ту же сущность (см. раздел 6).

## 2. Сценарии пошагово

### 2.1. Бот первым: «Привязать почту»

1. Пользователь нажимает кнопку «📧 Привязать почту» (или `/email`).
2. Бот сначала вызывает `GET /api/bot/status?telegram_id=…`:
   - `200` и `linked: true` → человек уже связан: показать экран «Уже
     связан» (2.4), дальше не идти;
   - `404` → не связан, продолжаем.
3. Бот просит ввести почту (FSM `email_wait_address`, таймаут 10 мин).
4. Бот вызывает `POST /api/bot/email/start {telegramId, email}`.
   - `200 {sent: true}` → «Код отправлен на <почта>. Введите 6 цифр из письма.»
     (FSM `email_wait_code`, таймаут 10 мин).
   - `200 {sent: false, alreadyLinked: true}` → «Эта почта уже привязана к вашему Telegram.» → экран 2.4.
   - `409 TELEGRAM_LINKED_OTHER` → «Ваш Telegram уже связан с другим
     аккаунтом сайта. Чтобы сменить почту, сначала отвяжите его.» + кнопка «Отвязать».
   - `400/429/502` → тексты из раздела 8.
5. Пользователь вводит код. Бот вызывает
   `POST /api/bot/email/confirm {telegramId, email, code, premiumPanelUserId?}`,
   где `premiumPanelUserId` — `remnawave_premium_id` из БД бота, если есть
   (необязательно: сайт найдёт `tg_{id}_premium` сам по username).
6. `200` → бот:
   - сохраняет у себя: `site_linked = true`, `site_user_id = data.userId`,
     `shared_panel_user_id = data.panelUserId`, `shared_sub_url = data.subscriptionUrl`,
     `email = data.email`;
   - если `data.kept == "site"` или `data.disabledPanelUserId == remnawave_premium_id`
     — помечает у себя старую премиум-сущность как отключённую сайтом
     (не удалять, не включать);
   - показывает экран «Готово» (2.3).
7. Ошибки кода — раздел 8 (`CODE_INVALID` с `attemptsLeft`, `CODE_EXPIRED`, …).

### 2.2. Сайт первым: ссылка из кабинета `/start link_<token>`

1. В кабинете сайта человек нажимает «Привязать Telegram» → сайт открывает
   `https://t.me/<бот>?start=link_<token>` (токен одноразовый, 15 минут).
2. Бот получает `/start link_<token>`. Токен — 43 символа `[A-Za-z0-9_-]`
   после префикса `link_` (старые постоянные токены — 16 hex без префикса,
   их тоже надо принимать: `/start <16hex>`).
3. Бот вызывает `GET /api/bot/link?token=<token>`:
   - `200 {valid: true, maskedEmail: "al***@mail.ru", telegramLinked}` →
     экран подтверждения: «Привязать аккаунт al***@mail.ru к этому
     Telegram?» Кнопки «✅ Привязать» / «Отмена». (FSM `link_confirm`, 15 мин.)
   - `404 TOKEN_INVALID`, `410 TOKEN_EXPIRED`, `410 TOKEN_USED` → «Ссылка
     недействительна или устарела. Получите новую в личном кабинете на сайте.»
4. «✅ Привязать» → `POST /api/bot/link {token, telegramId, premiumPanelUserId?}`.
   Ответ — как у confirm (2.1 п.6), те же действия бота.
5. «Отмена» → «Хорошо, ничего не меняли.» Токен не тратится.

### 2.3. Что показать после связки (по `data.kept`)

| `kept` | Что произошло | Сообщение |
|---|---|---|
| `bot` | обе подписки были, у бота срок больше; ключ бота стал общим, ключ сайта отключён | «Готово! Бот и сайт теперь работают с одной подпиской. Ваш ключ из бота остаётся — ничего перенастраивать не нужно. Подписка до {дата}.» |
| `site` | обе были, у сайта срок больше; ключ сайта общий, ключ бота отключён | «Готово! Общая подписка — та, что на сайте, до {дата}. ⚠️ Прежний ключ из бота отключён: обновите подписку в приложении по новой ссылке 👇» + `subscriptionUrl` + кнопки «Открыть в Happ» |
| `only-bot` | подписка была только в боте | «Готово! Ваша подписка из бота теперь видна и на сайте, ключ тот же. До {дата}.» |
| `only-site` | подписка была только на сайте | «Готово! Подписка с сайта до {дата}. Вот ваш ключ 👇» + `subscriptionUrl` |
| `none` | активной подписки нет ни там, ни там | «Готово! Аккаунты связаны. Активной подписки пока нет — оформите её в боте или на сайте.» |

Если `bonusDays > 0` — добавить строку «🎁 +{bonusDays} дней за привязку!».
Если `accountCreated: true` — «Мы создали аккаунт на сайте для {email}: войти можно по коду из письма.»

### 2.4. Уже связан

`GET /api/bot/status` вернул `linked: true` → «Ваш Telegram связан с
аккаунтом {email}. Подписка до {subscriptionEnd}.» Кнопки: «🔑 Мой ключ»
(показать `subscriptionUrl`), «Отвязать».

### 2.5. Смена почты

Смена почты = отвязка + привязка новой: если Telegram связан, `email/start`
с другой почтой вернёт `409 TELEGRAM_LINKED_OTHER`. Бот предлагает
«Отвязать», после успешной отвязки — снова сценарий 2.1 с новой почтой.
Ключ и подписка остаются у старого аккаунта сайта (см. 2.6).

### 2.6. Отвязка

1. Кнопка «Отвязать» → подтверждение: «Отвязать Telegram от аккаунта
   {email}? Подписка и ключ останутся в аккаунте на сайте. Бонус за
   повторную привязку не начисляется.» [Отвязать] [Отмена].
2. `POST /api/bot/unlink {telegramId}` → `200 {unlinked: true, keyStaysWithAccount: true}`.
3. Бот у себя: `site_linked = false`, `shared_panel_user_id = NULL`,
   `shared_sub_url = NULL`. **Сущность с общим ключом больше не его.**
4. Если человек потом покупает в боте — бот создаёт НОВУЮ премиум-сущность
   (см. 4.4: сущность с маркером `atlas-site:` не усыновлять).

## 3. Эндпоинты сайта

База: `https://qodev.dev`. Все запросы — JSON, заголовок
`X-Bot-Api-Key: <BOT_API_KEY>` (сравнение на сайте — timing-safe, как в
`verifyBotApiKey`). Неверный/пустой ключ → `401 {success:false, error:"Unauthorized"}`.

Формат: успех `{ "success": true, "data": {…} }`, ошибка
`{ "success": false, "error": "текст", "code": "КОД", …доп. поля }`.
Бот ветвится по `code`, текст `error` можно показывать как запасной.

Если админ выключил синхронизацию с ботом — все изменяющие вызовы отвечают
`503 {code: "bot_sync_disabled"}` (повторять позже, не показывать ошибку
человеку как окончательную).

### 3.1. `POST /api/bot/email/start`

```json
{ "telegramId": "738398394", "email": "alice@mail.ru" }
```

| Ответ | Когда |
|---|---|
| `200 {sent: true, expiresInSeconds: 600}` | код отправлен (или почта могла быть новой — ответ нейтральный: сайт НЕ сообщает, есть ли аккаунт с этой почтой) |
| `200 {sent: false, alreadyLinked: true}` | этот Telegram уже связан с этой почтой |
| `400 VALIDATION` | telegramId не цифры / почта некорректна / служебный адрес `telegram_…@tg.…` |
| `400 DISPOSABLE_EMAIL` | одноразовая почта |
| `409 TELEGRAM_LINKED_OTHER` | Telegram связан с другим аккаунтом сайта (сначала отвязка) |
| `429 RATE_LIMITED` + `retryAfterSeconds`, заголовок `Retry-After` | лимиты ниже |
| `502 EMAIL_SEND_FAILED` | письмо не ушло |

Лимиты: на Telegram ID — 3 кода за 10 минут и 10 за сутки; на почту — 3 за
10 минут и 10 за сутки; на IP бота — 120 запросов в минуту (общий клапан).
Новый `start` для того же Telegram ID заменяет предыдущий код.
Код: 6 цифр, 10 минут, 5 попыток, хранится отдельно от кодов входа на сайт.
Письмо: тема «Код для привязки Telegram к Atlas Secure».

```json
{ "telegramId": "738398394", "email": "alice@mail.ru", "code": "123456", "premiumPanelUserId": 4211 }
```

`200`:
```json
{
  "success": true,
  "data": {
    "linked": true,
    "alreadyLinked": false,
    "accountCreated": false,
    "userId": "2b1c…",
    "email": "alice@mail.ru",
    "telegramId": "738398394",
    "panelUserId": 4211,
    "subscriptionUrl": "https://sub.atlassecure.ru/AbCd…",
    "subscriptionEnd": "2026-10-20T12:00:00.000Z",
    "plan": "plus",
    "daysLeft": 37,
    "isExpired": false,
    "kept": "bot",
    "keptPanelUserId": 4211,
    "disabledPanelUserId": 1880,
    "bonusDays": 7,
    "panelSynced": true,
    "bypassPanelUserId": 4210,
    "telegramBonus": { "granted": true, "days": 7 },
    "subscriptionPlan": "plus",
    "vpnKey": "https://sub.atlassecure.ru/AbCd…",
    "hasActiveSubscription": true,
    "hoursLeft": 5,
    "xrayUuid": null,
    "referralCode": "SITE1234"
  }
}
```

- `kept`: `bot` | `site` | `only-bot` | `only-site` | `none` (см. 2.3).
- `disabledPanelUserId` — id отключённой сущности или `null`.
- `panelSynced: false` — связка в БД сайта завершена, но панель была
  недоступна; сайт досинхронизирует её сам (воркер, до ~1 ч с backoff).
  Боту делать ничего не надо.
- `subscriptionUrl` = `null`, если подписка истекла (как и в других ответах).

| Ошибка | Когда | Код остаётся годным? |
|---|---|---|
| `400 VALIDATION` | формат полей | да |
| `400 CODE_NOT_FOUND` | кода нет или он запрошен для другой почты | — |
| `400 CODE_EXPIRED` | прошло 10 минут | нет |
| `400 CODE_INVALID` + `attemptsLeft` | неверный код | да, пока `attemptsLeft > 0` |
| `400 CODE_ATTEMPTS_EXCEEDED` | 5 неверных попыток | нет |
| `409 TELEGRAM_LINKED_OTHER` | Telegram связан с другим аккаунтом | да |
| `409 EMAIL_LINKED_OTHER` | аккаунт с этой почтой связан с другим Telegram | да |
| `429 RATE_LIMITED` | много попыток с IP | да |
| `503 PANEL_UNAVAILABLE` / `503 BUSY` | панель не отвечает / параллельный запрос | **да — повторить тот же запрос** |

Идемпотентность: повтор успешного confirm с тем же кодом невозможен (код
тратится), но это и не нужно — повторная связка той же пары любым путём
(`/api/bot/link` с тем же токеном тем же Telegram ID) возвращает `200` с
`alreadyLinked: true`, `bonusDays: 0`, без повторного слияния.

### 3.3. `GET /api/bot/link?token=…` — предпросмотр

`200 {valid: true, kind: "one_time"|"legacy", maskedEmail, expiresAt, telegramLinked}`;
`404 TOKEN_INVALID`, `410 TOKEN_EXPIRED`, `410 TOKEN_USED`. Не тратит токен.
Принимает `link_<token>`, `<token>` и старый 16-hex.

### 3.4. `POST /api/bot/link`

```json
{ "token": "link_Qw3…", "telegramId": "738398394", "premiumPanelUserId": 4211 }
```

Ответ `200` — как 3.2. Ошибки: `400 VALIDATION`, `404 TOKEN_INVALID`,
`410 TOKEN_EXPIRED`, `410 TOKEN_USED` (использован другим Telegram),
`409 TELEGRAM_LINKED_OTHER | EMAIL_LINKED_OTHER`, `503 PANEL_UNAVAILABLE | BUSY`.
Токен тратится только успешной связкой; повтор тем же Telegram ID →
`200 alreadyLinked: true`. Старый постоянный токен срабатывает и сразу
заменяется новым.

`bypass` = `null`, если сущности обхода нет или панель не ответила за ~2,5 с

### 3.6. `POST /api/bot/unlink`

`{telegramId}` → `200 {unlinked: true, userId, email, panelUserId, keyStaysWithAccount: true}`;
`404 NOT_LINKED`. Подписка и ключ остаются у аккаунта сайта; сущность в
панели теряет `telegramId` и получает маркер `atlas-unlinked:<время>`.

### 3.6a. `POST /api/bot/relink` — миграция уже связанных

`{telegramId, premiumPanelUserId?}` → только для Telegram ID, который УЖЕ
связан: повторяет слияние ключей (раздел 9). Ничего нового не привязывает,
почту не меняет, идемпотентен. `200` — как 3.2; `404 NOT_LINKED`;
`503 PANEL_UNAVAILABLE | BUSY` — повторить.

### 3.7. `POST /api/bot/extend` (без изменений контракта, но теперь обязателен для связанных)

```json
{ "telegramId": "738398394", "days": 30, "plan": "plus", "amount": 299, "paymentId": "bot-pay-9f1c" }
```
Продлевает от max(сейчас, конец) через журнал сайта, сразу переносит срок в
общую сущность панели, начисляет кешбэк рефереру (как сейчас). **Всегда
передавайте `paymentId`** — повтор с тем же `paymentId` → `duplicate: true`,
ничего не применяется дважды. Ответ содержит `subscriptionUrl` и
`subscriptionEnd` — их и показывать.

### 3.8. Таймауты и ретраи

| Вызов | Таймаут HTTP бота | Ретраи |
|---|---|---|
| `email/start` | 15 с | нет авто-ретрая (иначе второе письмо); на сетевую ошибку — «Не удалось отправить, попробуйте ещё раз» |
| `email/confirm`, `POST link` | 30 с (сайт сам ждёт панель до ~15 с) | на таймаут/5xx/`503` — до 3 раз с паузой 2 с, 5 с, 10 с, ТЕМ ЖЕ телом |
| `status`, `GET link` | 10 с | до 2 раз |
| `extend` | 30 с | до 5 раз с тем же `paymentId` (идемпотентно), затем очередь фоновых повторов |
| `unlink` | 15 с | до 3 раз (повтор после успеха → `404 NOT_LINKED`, это тоже успех) |

`429` — ждать `retryAfterSeconds`, человеку: «Слишком много попыток,
подождите N сек.»

## 4. Изменения в логике покупки и в ведении премиум-сущности

### 4.1. Перед любой выдачей/продлением премиум

```
st = GET /api/bot/status?telegram_id=ID
if st == 200 and st.data.linked:
    СВЯЗАННЫЙ → 4.2
else:
    НЕ СВЯЗАННЫЙ → логика как раньше (tg_{id}_premium, preflight, adopt, PATCH expireAt), но с 4.4
```
Кешировать `status` можно не дольше 60 с. Если сайт недоступен (таймаут/5xx)
и в БД бота `site_linked = true` — считать связанным (4.2) и ставить продление
в очередь; НИКОГДА не падать обратно на создание `tg_{id}_premium`.

### 4.2. Связанный человек покупает премиум в боте

1. Принять оплату как обычно.
2. `POST /api/bot/extend {telegramId, days, plan, amount, paymentId}` — ЕДИНСТВЕННОЕ действие с подпиской.
3. **НЕ** создавать и **НЕ** адоптить `tg_{id}_premium` как отдельный ключ.
4. **НЕ** делать `PATCH expireAt` (и никакой другой PATCH) сущности
   `st.data.panelUserId` — ею управляет сайт.
5. Показать ключ из ответа `extend` (`subscriptionUrl`), срок — `subscriptionEnd`.
6. `POST /api/bot/sync-balance` — как и раньше (кешбэк).

Если `extend` не прошёл после ретраев — оплата у бота остаётся, продление
ставится в очередь повторов с тем же `paymentId`; человеку: «Оплата принята,
подписка продлится в течение нескольких минут.»

### 4.3. `POST /api/bot/sync` (overwrite_site) для связанных

Не вызывать для продлений. Допустимо только для явного отзыва подписки
(`plan: "none"`). Перезапись датой из БД бота укоротит общий ключ.

### 4.4. Preflight и адопт `tg_{id}_premium` (для НЕсвязанных)

Сайт дописывает к описанию сущности свои маркеры через ` | `:
`atlas-site:<id аккаунта>`, `atlas-email-verified:<время>`, `atlas-unlinked:<время>`.
Текст бота («Premium via bot (plus)») не трогается.

Правило адопта в боте (дополнить существующее): НЕ адоптить сущность, если
в её `description` есть `atlas-site:` — это ключ аккаунта сайта (например,
после отвязки ключ остался на сайте). В этом случае создать новую сущность с
username `tg_{id}_premium_2` (далее `_3`, … — первое свободное), остальные
поля как раньше.

### 4.5. Что сайт делает с сущностями бота (для понимания)

- Оставленная при слиянии сущность бота: сайт пишет `email`, `telegramId`,
  маркеры в description, тег `SITE_BASIC/PLUS` (бот тегов не использует) и
  `expireAt`/`status: ACTIVE` при продлениях. Сайт **не меняет** её `username`,
  `hwidDeviceLimit`, `externalSquadUuid`, сквады, трафик-стратегию.
- Проигравшая сущность: только `status: DISABLED`, срок не трогается, не удаляется.
- Если панель у общей сущности показывает срок ПОЗЖЕ, чем в БД сайта, и он
  изменился не сайтом (старый код бота продлил сам), — сайт подтягивает этот
  срок к себе и не укорачивает ключ. Это страховка на время выкладки, а не
  рабочий путь: продлевать нужно через `extend`.

## 5. Обход (bypass) после связки

1. Бот ведёт `{telegram_id}` как раньше: создание, покупки трафика в боте,
   лимит трафика, `expireAt` 2099, сквад обхода
   `6947418d-83b6-4050-a10c-3829e4cd4b2c`, лимит устройств 5 (те же
   значения сайт будет ставить своим сущностям обхода в следующей фазе).
2. Сайт запоминает эту сущность за аккаунтом (`bypass_panel_user_id`), не
   трогает её `expireAt`, сквад, лимит устройств, стратегию трафика и
   никогда не синхронизирует её как ключ премиум.
3. **Сайт продаёт «Пакеты трафика» (с 13.09.2026) и прибавляет ГБ в ту же
   сущность обхода.** Цены — те же, что в боте (`src/lib/traffic-packs.ts`
   сайта: 15 ГБ / 89 ₽ … 5000 ГБ / 17 999 ₽). У связанного человека сайт
   прибавляет купленные ГБ **в ботовскую `{telegram_id}`** — read-modify-write
   `trafficLimitBytes`, идемпотентно по id платежа (журнал
   `bypass_traffic_ops`, op `grant:payment:<id>`), никогда не сбрасывая и не
   записывая абсолютное значение из своей БД; срок, сквад, лимит устройств и
   стратегию трафика не трогает. Поэтому бот ОБЯЗАН:
   - добавлять трафик только как read-modify-write: `GET /api/users/{id}` →
     `trafficLimitBytes + пакет` → `PATCH trafficLimitBytes`; никогда не
     записывать значение из своей БД (иначе затрёт ГБ, купленные на сайте);
   - **перед каждым показом остатка ГБ перечитывать** сущность из панели или
     брать `bypass` из `GET /api/bot/status` — не показывать кеш своей БД;
   - делать покупку трафика идемпотентной по id платежа (запомнить
     `base_limit` до PATCH; на повторе: текущий = base → применить,
     = base + пакет → уже применено, иное → ручная проверка, не гадать);
   - **только прибавлять** — никаких «установить лимит = N».
4. Связанный человек без ботовского обхода, купивший пакет на сайте:
   сайт создаёт СВОЮ сущность `ST<8 цифр>_bp` (сквад обхода, 2099,
   `NO_RESET`, 5 устройств, тег `SITE_BYPASS`, маркер `atlas-site:<id>`).
   Её id приходит в `status.bypass.panelUserId`, `status.bypassOrigin =
   "site"`. Бот в этом случае **не создаёт** свою `{telegram_id}`, а докупку
   в боте прибавляет в `status.bypass.panelUserId` тем же read-modify-write.
5. Если при связке обход был с обеих сторон: остаток (лимит − использовано)
   второй сущности прибавляется к `{telegram_id}` бота, вторая — `DISABLED`.
   Правило подтверждено владельцем 13.09.2026. Сайт это делает сам при
   связке; при отвязке сайт оставляет у аккаунта только свою `ST…_bp`,
   ботовская `{telegram_id}` остаётся боту.
6. Пробный период на сайте = 3 дня премиум + 500 МБ обхода (500 × 1024² =
   524 288 000 байт) — один раз на человека, той же защитой от
   злоупотреблений, что пробный премиум. Выдаётся в `ST…_bp` при регистрации
   на сайте. Регистрация через бота (`/api/bot/register`) пробный обход
   сайта НЕ получает — бот даёт свой. Если у связанного уже есть обход бота,
   пробные 500 МБ сайта не выдаются. Поле `status.bypassTrialGranted: true`
   — сайт уже выдал пробный обход: бот свой пробный (500 МБ) повторно не выдаёт.
7. Покупки на сайте бот узнаёт без вебхуков — опросом `GET /api/bot/status`
   (растёт `bypass.limitBytes`). `status.bypassOwedBytes > 0` — оплачено на
   сайте, но панель ещё не приняла (сайт повторит сам): показать «гигабайты
   зачисляются», **самому не прибавлять**. При каждом открытии экрана обхода
   и после оплаты — перечитать.
8. Названия (одинаковые на сайте и в боте): публичная витрина — «Пакеты
   трафика»; экраны для своих (бот, кабинет) — «Обход». Два ключа
   показываются подписанными — см. раздел 6, «Два ключа».

## 7. Состояния (FSM) и таймауты

```
idle
 ├─ «Привязать почту» ─▶ email_wait_address (10 мин)
 │      ├─ ввод почты ─▶ start ─200 sent─▶ email_wait_code (10 мин, 5 попыток)
 │      │                         ├─ ввод кода ─▶ confirm ─200─▶ idle (экран «Готово»)
 │      │                         ├─ CODE_INVALID ─▶ email_wait_code
 │      │                         ├─ CODE_EXPIRED|ATTEMPTS ─▶ email_wait_address («Отправить ещё раз»)
 │      │                         └─ 503/сеть ─▶ email_wait_code (повтор тем же кодом)
 │      └─ 409/400 ─▶ idle или email_wait_address
 └─ /start link_<token> ─▶ GET link ─200─▶ link_confirm (15 мин)
        ├─ «Привязать» ─▶ POST link ─200─▶ idle («Готово»)
        └─ «Отмена» / таймаут ─▶ idle
```
По истечении таймаута состояния — молча вернуться в `idle`; на следующее
сообщение ответить главным меню. В `email_wait_code` принимать только
`^\d{6}$` (пробелы убрать); почту хранить в данных FSM, не в БД бота, до
успешного confirm.

## 9. Миграция существующих пользователей

1. Уже связанные старым способом (на сайте у них есть `telegram_id`): до
   этой версии у них могут быть ДВЕ живые премиум-сущности — ST сайта и
   `tg_{id}_premium` бота. Одноразовый проход после выкладки бота:
   для каждого Telegram ID, который бот считает связанным с сайтом (или для
   всех, у кого есть `remnawave_premium_id`):
   ```
   st = GET /api/bot/status?telegram_id=ID
   if st == 200 and st.data.panelUserId != remnawave_premium_id:
       POST /api/bot/relink {telegramId: ID, premiumPanelUserId: remnawave_premium_id}
   ```
   Сайт выполнит то же слияние, что и при новой связке (больший срок
   остаётся, второй ключ `DISABLED`, дни не складываются), и вернёт ответ
   как у `/api/bot/link`. Если человек никогда не получал бонус за
   привязку — получит +7 сейчас (один раз). Проход можно повторять:
   `relink` идемпотентен. Темп — не чаще 5 запросов в секунду. Людям с
   `kept: "site"` бот отправляет сообщение из таблицы 2.3 (ключ бота
   отключён — нужна новая ссылка). До прохода сайт страхует ключ правилом
   «не укорачивать» (4.5).
2. Несвязанные — ничего не делать; они привяжутся сами.
3. Аккаунты-заглушки `telegram_<id>@tg.atlassecure.uk`, созданные
   `/api/bot/register`, при привязке почты переименовываются в настоящую
   почту (дубля не будет); если у почты уже есть аккаунт — заглушка
   поглощается им (срок — больший из всех, лишний ключ отключается).
4. Поле БД бота `remnawave_premium_id` у связанных больше не источник
   правды о ключе; источник — `status.panelUserId` / `subscriptionUrl`.

## 11. Порядок выкладки

1. **Сначала сайт.** Миграции добавляющие (новые таблицы и колонки), старые
   эндпоинты обратно совместимы: `/api/bot/link` принимает старые токены,
   ответы расширены новыми полями. Env (все необязательные):
   `TELEGRAM_BOT_USERNAME` (без @, для ссылки из кабинета),
   `BOT_PREMIUM_USERNAME_PATTERN` (по умолчанию `tg_{telegram_id}_premium`),
   `BOT_BYPASS_USERNAME_PATTERN` (по умолчанию `{telegram_id}`),
   `REMNAWAVE_BYPASS_SQUAD_UUID` (по умолчанию `6947418d-83b6-4050-a10c-3829e4cd4b2c`),
   `REMNAWAVE_BYPASS_DEVICE_LIMIT` (по умолчанию 5) — для следующей фазы.
   **Сквад и лимит устройств обхода у бота и сайта должны совпадать:**
   бот ставит обходу сквад `REMNAWAVE_CLIENTS_SQUAD_UUID` /
   `REMNAWAVE_SQUAD_UUID` — у бота это должен быть тот же
   `6947418d-83b6-4050-a10c-3829e4cd4b2c`, лимит устройств — 5
   (`REMNAWAVE_BYPASS_DEVICE_LIMIT` бота). Проверьте значения в env бота.
2. Проверить на сайте: `GET /api/bot/status` для известного связанного
   Telegram ID; `POST /api/bot/email/start` на тестовую почту — письмо
   пришло; в кабинете «Привязать Telegram» открывает бота.
3. **Потом бот** с этой логикой. Шаблоны username в боте и на сайте
   должны совпадать (`REMNAWAVE_PREMIUM_USERNAME_PATTERN` бота ↔
   `BOT_PREMIUM_USERNAME_PATTERN` сайта).
4. После выкладки бота проверить:
   - в журнале админки сайта события `telegram.link` с `kept=…`;
   - в панели у связанных: одна живая премиум-сущность на человека,
     вторая `DISABLED`;
   - покупка в боте связанного → событие «Продление ботом» в карточке
     пользователя, в панели новый `expireAt` на общей сущности;
   - нет событий «Срок из панели (общий ключ)» после новых покупок (их
     появление значит, что бот всё ещё PATCH-ит `expireAt` сам).
